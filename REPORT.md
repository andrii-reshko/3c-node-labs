## 1. Завдання та їх виконання

### Завдання 1. Версіонування API

Всі існуючі маршрути перенесено під префікс `/api/v1`. Нові маршрути v2 зареєстровано під `/api/v2`. Реалізовано через механізм `prefix` при реєстрації плагінів у Fastify (`app.js`):

```js
fastify.register(v1, { prefix: '/api/v1' });
fastify.register(v2, { prefix: '/api/v2' });
```

Маршрути розділено на окремі файли: `http/routes/v1.js` і `http/routes/v2.js`.

---

### Завдання 2. Коректні HTTP статус-коди

Всі ендпоінти повертають семантично правильні коди відповіді:

| Операція | Код |
|----------|-----|
| GET (знайдено) | `200 OK` |
| POST (створено) | `201 Created` |
| PATCH/DELETE (успішно) | `200 OK` |
| Не знайдено | `404 Not Found` |
| Некоректний запит | `400 Bad Request` |
| Серверна помилка | `500 Internal Server Error` |
| Перевищено ліміт | `429 Too Many Requests` |

### Завдання 3. Пагінація для `/api/v2/device`

Реалізовано новий ендпоінт `GET /api/v2/device` з підтримкою пагінації. `/api/v1/device` залишився без змін.

**Параметри запиту:** `?page=1&limit=10` (за замовчуванням `page=1`, `limit=10`).

**Формат відповіді:**
```json
{
  "data": [...],
  "meta": {
    "total": 30,
    "page": 1,
    "limit": 10,
    "totalPages": 3
  }
}
```

Реалізовано через `storage.findAllPaginated(page, limit, filter)` у `repository/device.repository.js` та `services/device.service.js`.

### Завдання 4. Rate Limiting

Підключено плагін `@fastify/rate-limit` з глобальним обмеженням у 100 запитів на хвилину з однієї IP-адреси:

```js
fastify.register(rateLimit, {
  max: 100,
  timeWindow: '1 minute',
});
```

При перевищенні ліміту сервер повертає `429 Too Many Requests`. До кожної відповіді автоматично додаються заголовки:

- `X-RateLimit-Limit` — максимальна кількість запитів за період
- `X-RateLimit-Remaining` — кількість запитів, що залишилась
- `Retry-After` — секунди очікування перед повторним запитом

Підключено `@fastify/swagger` та `@fastify/swagger-ui`. Документація доступна за адресою `GET /docs`.

### Завдання 6. Інтеграція із зовнішнім сервісом через fetch

**Варіант 5 — типи пристроїв:**
```json
[{ "id": 1, "type": "lamp", "powerWatt": 10 }]
```

Зовнішній сервер запускається командою `npm run external` (json-server на порту `3002`).

Реалізовано ендпоінт `GET /api/v1/device/:id/details`, який:
1. Отримує запис пристрою з файлового сховища
2. Робить fetch до `http://localhost:3002/deviceTypes`
3. Повертає об'єднану відповідь: пристрій + поле `power` (powerWatt з типу)

**Реалізовано у `repository/remote.repository.js`:**

- **Retry з exponential backoff** — 3 спроби з затримками 1s, 2s, 4s
- **Timeout через AbortController** — 5 секунд на запит
- **Кешування відповідей** — TTL 5 хвилин (`utils/cache.js`)
- **Graceful degradation** — при недоступності зовнішнього сервісу повертається пристрій з `power: null` замість помилки

### Завдання 7. GitHub API інтеграція

Реалізовано ендпоінт `GET /api/v{1,2}/github/shared-repos?repo={owner/repo}` — повертає топ-5 репозиторіїв зі спільними контриб'юторами.

**v1 (`/api/v1/github/shared-repos`)** — реалізовано через **GitHub REST API** за допомогою `@octokit/rest`:

```js
// repository/github.rest.js
import { Octokit } from '@octokit/rest';
```

Алгоритм:
1. `octokit.repos.listContributors` — топ-30 контриб'юторів цільового репо
2. `octokit.repos.listForUser` — репозиторії кожного контриб'ютора (без форків)
3. `octokit.repos.listContributors` — контриб'ютори кожного кандидата
4. Підрахунок перетину → сортування → топ-5

**v2 (`/api/v2/github/shared-repos`)** — реалізовано через **GitHub GraphQL API** за допомогою `@octokit/graphql`:

```js
// repository/github.gql.js
import { graphql } from '@octokit/graphql';
```

Алгоритм ідентичний, але замість REST використовується GraphQL із пагінацією по `defaultBranchRef.target.history` (до 1000 комітів) для визначення реальних контриб'юторів.

## 3. Контрольні запитання

**1. Що таке REST і які його основні принципи?**

REST (Representational State Transfer) — архітектурний стиль побудови розподілених систем на основі HTTP. Основні принципи:
- **Stateless** — сервер не зберігає стан клієнта між запитами
- **Ресурси** — кожна сутність має унікальний URI (`/device`, `/device/1`)
- **Уніфікований інтерфейс** — HTTP-методи визначають операцію (GET, POST, PATCH, DELETE)
- **Клієнт-сервер** — незалежність клієнта і сервера
- **Кешованість** — відповіді можуть кешуватись на стороні клієнта

**2. Навіщо версіонувати API і як це реалізовано у Fastify?**

Версіонування дозволяє змінювати API без порушення роботи існуючих клієнтів. При зміні поведінки ендпоінту — зміни вносяться в нову версію, стара залишається незмінною. У Fastify реалізується через параметр `prefix` при реєстрації плагінів: `fastify.register(routes, { prefix: '/api/v1' })`.

**3. Що таке пагінація і які параметри вона використовує?**

Пагінація — механізм розбиття великого набору даних на сторінки для зменшення навантаження. Параметри передаються через query string: `?page=1&limit=10`. Відповідь містить масив даних і метаінформацію: `total`, `page`, `limit`, `totalPages`.

**4. Що таке Rate Limiting і навіщо він потрібен?**

Rate Limiting — механізм обмеження кількості запитів від одного клієнта за певний проміжок часу. Захищає сервер від перевантаження та зловмисного використання (DDoS, brute force). При перевищенні ліміту сервер повертає `429 Too Many Requests`. Заголовки `X-RateLimit-Limit`, `X-RateLimit-Remaining` інформують клієнта про поточний стан ліміту.

**5. Для чого потрібен Swagger (OpenAPI)?**

Swagger — стандарт опису REST API у форматі JSON/YAML. Переваги:
- Дозволяє тестувати ендпоінти безпосередньо в браузері без Postman
- Слугує контрактом між бекенд і фронтенд розробниками
- Документація завжди актуальна (генерується автоматично з коду)
- Можна генерувати клієнтські бібліотеки для різних мов

**6. Як працює нативний fetch в Node.js? Чим відрізняється від інших HTTP-клієнтів?**

Починаючи з Node.js 18, `fetch` доступний глобально без залежностей. Повертає `Promise<Response>`. Головна відмінність: **не кидає виключення при HTTP-помилках** (4xx, 5xx) — лише при мережевих помилках. Тому необхідно явно перевіряти `response.ok` або `response.status`.

**7. Що таке retry з exponential backoff?**

Retry — повторний запит після невдалого. Exponential backoff — стратегія збільшення затримки між спробами в геометричній прогресії: 1s → 2s → 4s. Запобігає перевантаженню сервісу при масових повторних запитах.

**8. Навіщо використовувати AbortController з fetch?**

`AbortController` дозволяє скасувати fetch-запит. Використовується для встановлення timeout: якщо зовнішній сервер не відповів за визначений час, запит скасовується і звільняються ресурси. Без timeout запит може "зависнути" назавжди.

**9. Що таке кешування відповідей зовнішнього сервісу і яка його перевага?**

Кешування зберігає результат запиту разом з часом запису. При повторному запиті перевіряється TTL (Time To Live) — якщо дані ще актуальні, повертаються з кешу без нового запиту до зовнішнього сервісу. Переваги: зменшення кількості зовнішніх запитів, прискорення відповіді, стійкість до тимчасової недоступності сервісу.

**10. Що таке Graceful Degradation?**

Graceful Degradation — підхід при якому відмова залежного сервісу не призводить до повної відмови основного. При недоступності зовнішнього сервісу система повертає частково заповнену відповідь замість помилки. Наприклад, при недоступності `json-server` ендпоінт `/device/:id/details` все одно повертає дані пристрою, лише з `power: null`.

**11. Яка різниця між GitHub REST API та GraphQL API?**

| | REST API | GraphQL API |
|---|---|---|
| Протокол | HTTP GET/POST | HTTP POST |
| Ендпоінт | Окремий URL для кожного ресурсу | Один URL `/graphql` |
| Дані | Фіксована структура відповіді | Клієнт сам визначає структуру |
| Over/Under-fetching | Проблема надлишкових або нестачі даних | Отримуємо рівно те, що запитали |
| Пагінація | `per_page` + `page` | Cursor-based (`pageInfo.endCursor`) |
| Бібліотека | `@octokit/rest` | `@octokit/graphql` |

## 4. Висновки

У ході лабораторної роботи набуто практичні навички:

- **Версіонування API** через механізм `prefix` у Fastify — реалізовано v1 і v2
- **Пагінація** — новий формат відповіді з метаінформацією для `/api/v2/device`
- **Rate Limiting** — захист сервера від перевантаження за допомогою `@fastify/rate-limit`
- **Swagger документація** — автоматична генерація з JSON Schema маршрутів
- **Інтеграція з зовнішнім сервісом** — fetch з retry, timeout через AbortController, TTL-кешування, graceful degradation
- **GitHub API** — реалізація одного алгоритму двома способами: через REST (`@octokit/rest`) та GraphQL (`@octokit/graphql`)
